v1 — Contract Repository (June 2026)

June 2026
shipped

This phase is captured as structured build-history notes.

What it was

The bootstrap of mariusw/urd-contract as the single source of truth for the Canonical Message wire format published by every Ratatoskr bridge. Before this repository existed, no shared definition of the Message type existed; the goal of Plan 0 was to make sure ratatoskr, vault, and every other consumer derive the format from one place rather than redefining it locally. This is the foundation every downstream plan depends on.

Key decisions

A single JSON Schema (message.schema.json) is the authoritative definition; everything else is derived from it. Generated language bindings are checked in (not generated at consume time) so downstream modules can depend on the repo without running codegen, and CI guards that the committed output stays in sync with the schema.

The sharpest decision was how to produce the Go binding. The plan's first choice was go-jsonschema, but its output diverged badly from the required wire shape: it named the type MessageSchemaJson, used Id/Cwd casing instead of the idiomatic ID/CWD, emitted pointer types and custom enum types, attached yaml/mapstructure tags we don't want, and produced an invalid omitempty,omitzero tag. Rather than fight the generator with post-processing, the Go struct is hand-authored from the schema and a field-parity test (generated/go/parity_test.go) is the correctness mechanism. The test asserts the struct's JSON tags exactly cover the schema's properties and that the required/omitempty split matches the wire contract — git_branch always present, parent_session_id omitted when absent. This keeps "schema is the single source of truth" true for Go without depending on a generator whose output we'd have to override anyway. TypeScript was left on json-schema-to-typescript, whose output is clean and deterministic, so it is still genuinely generated by make generate.

The stale go install path in the plan (cmd/go-jsonschema, which no longer exists) became moot once go-jsonschema was dropped from the generate path entirely; CI no longer installs it.

What shipped
  • message.schema.json — draft-07 JSON Schema defining all eleven Message fields, enums for harness and role, and additionalProperties: false
  • generated/go/message.go — hand-authored Go struct matching the wire shape, plus constants.go (NATS subject, detached-branch sentinel, typed harness/role values)
  • generated/go/parity_test.go — field-set and required/omitempty parity tests against the schema
  • generated/ts/message.ts (generated) and generated/ts/constants.ts (handwritten)
  • Makefile — generate regenerates the TypeScript; verify runs the Go tests and fails on any drift between schema and committed generated output
  • .github/workflows/validate.yml — CI that regenerates and verifies on every push and PR, pinning Go via go.mod
Limitations that drove the next phase

This repository only defines the contract; it does not yet have a consumer. Plan 1 adds it as a Go dependency to the first bridge. CI has not been exercised against a real remote yet — there is no GitHub remote configured, so the validate workflow has only been replicated locally. The parity test covers field names and presence semantics but does not assert type-level correspondence (e.g. that timestamp is a time.Time mapping to a date-time string); that has been acceptable so far because the struct is small and hand-reviewed.

Gaps identified at review
  • No go vet or lint step in CI. For a contract repository that others depend on, a lint pass would be cheap insurance.
  • TypeScript verify doesn't compile-check. The plan had npx tsc --noEmit --strict, but make verify only checks git diff. If json-schema-to-typescript ever produces invalid TypeScript, it won't be caught until a consumer imports it. Adding a tsc step to verify would close this gap.
  • No versioning strategy. The contract repo has no semver tags. Once ratatoskr and vault start importing it, there's no way to signal breaking changes. Even v0.1.0 now would establish the practice.
  • Go module version may cause CI mismatch. go.mod declares go 1.26.2, which hasn't been released as stable. The CI uses go-version-file: go.mod, so if the runner doesn't have a 1.26 toolchain, the job will fail. Pin to a released Go version.
  • Import path is generated/go, not the module root. Consumers write contract "github.com/mariusw/urd-contract/generated/go". If more Go code is added at the root later, the package structure will need rethinking.

v2 — Generation Restored (June 2026)

June 2026
shipped

This phase is captured as structured build-history notes.

Problem

The v1 Go binding was hand-authored, which is the exact opposite of the reason this repository exists. The whole premise is that message.schema.json is the single source of truth and every binding falls out of it; a hand-written message.go policed by a parity test just recreated the v1/v2 ratatoskr arrangement (a canonical hand-written Go type kept in sync with a second representation) that this repo was built to abolish. The manual-sync debt had changed clothes, not disappeared.

Root cause, not just the symptom

The hand-authoring wasn't a tooling failure. The plan specified an exact "required Go struct shape" (idiomatic ID/CWD casing, plain-string enums, a Message type name) lifted almost verbatim from the old ratatoskr hand-written struct. That shape spec was a second source of truth competing with the schema. Once you assert both the schema and the shape of what it must generate, any gap between them forces either generator-fighting or hand-editing. The fix was therefore to delete the requirement, not to satisfy it: stop dictating the Go shape and accept whatever the generator emits as the contract.

The earlier claim that go-jsonschema "couldn't" produce the wanted shape was also just wrong, asserted from memory rather than from --help. It has flags for capitalization, tag selection, and root-type naming. But by the root-cause logic above, most of those flags should not be used, because each one imposes a preference the schema does not express. The clean test: configuration that makes the generator honor the schema more faithfully is legitimate; configuration that imposes external taste is a smuggled second authority. Only -t survives that test (it tells the generator to take the type name from the schema's own title, instead of the file name, which would otherwise yield MessageSchemaJson).

What shipped
  • generated/go/message.go is now genuinely generated by go-jsonschema -p contract -t. Accepted as-is: Id/Cwd casing, pointer optionals, typed MessageHarness/MessageRole enums with strict unmarshalling, and the default yaml/mapstructure tags. None of these affect the JSON wire format, which is governed solely by the json tags.
  • generated/go/parity_test.go is deleted. It only existed to police a hand-written file; with real generation there is nothing to drift, and CI's regenerate-and-diff is the guard.
  • constants.go is trimmed to NATSSubject and DetachedBranch, the only two values the schema cannot express. Harness and role values now come from the generated typed enums.
  • Makefile generate runs both generators; the Go invocation uses $(shell go env GOPATH)/bin/go-jsonschema so it works without relying on PATH. CI reinstates go install github.com/atombender/go-jsonschema@latest (corrected module path, not the stale cmd/... subpath).
What it deliberately omits

No attempt to prettify the generated output. Id/Cwd reads as non-idiomatic Go, but it is lint-exempt generated code with zero wire impact, and matching it to taste is exactly the second-source-of-truth trap that caused this. If a consumer ever needs idiomatic accessors, that belongs in consumer code, not in overriding the generator here.

v3 — Flattened Layout (June 2026)

June 2026
shipped

This phase is captured as structured build-history notes.

Problem

Consumers had to import github.com/mariusw/urd-contract/generated/go. The word "generated" in a public import path is redundant signaling, the generated-ness is already carried by each file's Code generated ... DO NOT EDIT header, and it leaks into the one place it has a cosmetic cost and no functional benefit.

Design decision

Drop generated/ entirely rather than rename it. The Go package moves to the module root, which is Go's own convention for a module's primary package and yields the clean import "github.com/mariusw/urd-contract" used as contract.Message. TypeScript moves to ts/, because TS has no root-package convention and mixing .ts beside .go at the root just crowds two languages into one directory; TS's path is not a public import identifier, so a subdirectory there costs nothing. The asymmetry (Go at root, TS in ts/) reflects each ecosystem's norm rather than being arbitrary.

The rejected alternative was keeping the files under generated/ and adding a hand-written root package that re-exports them with type aliases. That would reintroduce a hand-maintained surface tracking the schema, the exact second-source-of-truth trap removed in v2. Moving the files has no such cost.

What shipped
  • message.go and constants.go at the module root, package contract. Import path is now github.com/mariusw/urd-contract.
  • message.ts and constants.ts under ts/.
  • generated/ deleted. Makefile generate writes to the new paths; verify diffs message.go and ts/message.ts.

This closes the "import path is generated/go" gap from the v1 review.

v4 — Hardening and First Release (June 2026)

June 2026
shipped

This phase is captured as structured build-history notes.

Problem

The contract was correct but not yet defensible or shippable. The v1 review had flagged five gaps; v3 closed the import-path one, leaving four: no lint pass, no TypeScript compile check, no semver, and a confused note about the Go version. With the repo about to gain a real remote and downstream consumers, these are the difference between a contract others can safely depend on and one that breaks silently.

What shipped
  • make verify now runs go vet ./... and npx tsc --noEmit --strict ts/message.ts ts/constants.ts in addition to the build and the schema-drift diff. CI invokes make verify, so both checks run on every push and PR. The TypeScript check matters most: json-schema-to-typescript output was previously only diffed, never compiled, so invalid TS would have surfaced only when a consumer imported it.
  • go.mod declares go 1.26 rather than go 1.26.2. The earlier note that "1.26.2 is not stable" was simply wrong — 1.26.2 is released and is the locally installed toolchain. The real reason to drop the patch is that the go directive sets a minimum-Go floor for consumers, and a patch-level floor needlessly excludes anyone on 1.26.0 or 1.26.1. For a contract library that exists to be imported widely, the floor should be as low as the language features require, which is go 1.26.
  • The GitHub remote was created private and the initial history pushed, so the validate workflow runs in real CI for the first time rather than only being replicated locally.
  • Tagged v0.1.0 to establish semver before any downstream consumer pins a version. The 0.x line signals the contract may still move; the practice of tagging at all is what matters now.
What it deliberately omits

No golangci-lint, only go vet. For a single generated struct plus two constants, vet is the right amount of static checking; a full linter config would be ceremony with nothing to catch. It can be added if the repo grows hand-written Go.

v5 — Drop sequence (June 2026)

June 2026
shipped

This phase is captured as structured build-history notes.

Problem

The schema contained a sequence field — an integer assigned by each bridge to track per-session message order. Analysis of the full system's design during the Plan 0 v3 grilling session revealed that sequence is unnecessary complexity: a session is a single agent process on a single machine, so wall-clock order within a session is reliable and sufficient for ordering. Any consumer that needs to sort messages within a session can sort by timestamp. No two sessions share a machine, so there is no cross-session clock ambiguity to resolve via sequence either. Downstream plans (1 through 4) were also authored without sequence as a result of that grilling session — meaning the contract was the only component that still carried it after the decisions crystallised.

There was also a collision between this repo's state and the downstream plan documents. The v3 plans were written against an earlier shape (idiomatic ID/CWD field casing, plain-string harness/role constants, a generated/go/ import path) that the repo had moved away from across phases v2 and v3. An attempted fix branch (fix/align-with-v3-plan) tried to revert the repo toward the plans, which was the wrong direction: it would have reintroduced the hand-written Go binding problem that v2 diagnosed and removed, and would have broken CI (the Makefile's generate target would clobber the hand-written file on every run). The full analysis lives in the ratatoskr repo's docs/BUILD-HISTORY.md, under the "Contract alignment - urd-contract v0.2.0" entry. The correct resolution is to drop sequence from the contract (the one change the plans were right about) and update the plan documents to match the contract's actual generated shape rather than revert the contract.

What shipped
  • sequence removed from message.schema.json: dropped from required and from properties.
  • message.go regenerated: Sequence int field and its UnmarshalJSON required-check are gone. The timestamp description now reads "Message production time. Used for ordering within a session — no sequence field exists."
  • ts/message.ts regenerated: sequence: number removed; same description added to timestamp.
  • Top-level schema description updated to mention the NATS subject explicitly.
  • Plans 1 through 4 in the ratatoskr repo are updated to match the contract's actual generated API shape (field names, constant names, import paths).
What it deliberately does not change

The generated-output-is-the-contract principle from v2, the flat layout from v3, and the harness/role typed enums. Those decisions are sound and remain. The plan documents are updated to match the contract, not the other way around.

v6 - Node runtime surface for TypeScript consumers (June 2026)

June 2026
shipped

This phase is captured as structured build-history notes.

Problem

The repository called itself the single source of truth, but only the Go half was actually true. Go consumers compile against a real module; TypeScript consumers had nothing to import at runtime. The ts/ directory held only .ts source, the package was type: "commonjs" with a main pointing at an index.js that did not exist, and there was no exports map. make verify ran tsc --noEmit, which stays green because TypeScript resolves a .js specifier back to its .ts sibling during typechecking, so the gap was invisible to every check we had. A consumer that typechecks import { NATS_SUBJECT } from "urd-contract/constants" would compile fine and then crash at runtime, because no shipped JavaScript file backs that import. The pi-bridge plan surfaced this: it is the first TypeScript consumer, it compiles to plain JavaScript run under Node, and that is exactly the case the old layout could not serve.

The deeper point is that this was a contract packaging bug, not a consumer bug. If every TypeScript bridge had to copy constants locally or invent a path alias to work around the missing surface, the contract would have stopped being central, and the runtime values would have splintered into each consumer, which is the wrong dependency direction and the precise failure this repository exists to prevent.

Design decision

Expose a real ESM package surface and make the public TypeScript API urd-contract/message and urd-contract/constants, backed by compiled files under dist/ and an explicit exports map. The ts/ directory stays as internal source layout and is no longer the consumer-facing path. The package becomes type: "module"; no dual CJS build was added, because no consumer needs CommonJS and speculative dual-publishing is debt without a payer. The asymmetry between the two subpaths is intentional and load-bearing: constants carries runtime values, so it must emit real JavaScript; message exports only a type, so tsc emits an essentially empty module (export {}), which is correct: a type-only import erases at compile time and needs no runtime backing. That same erasure is why a consumer can import type from a package that ships no value JS, and why constants cannot rely on it.

Committing dist/ to git is deliberate. The contract is consumed as a local file: dependency, and npm does not run a build step for a linked dependency, so the compiled JavaScript has to already be on disk when a consumer installs. The drift guard in make verify was extended to cover dist/ for the same reason it already covered the generated Go and TS source: a committed artifact that can fall out of sync with its source needs a check that fails loudly. Because tsc output is deterministic for a given TypeScript version and build:ts runs earlier in verify, the guard catches a stale committed dist/ rather than a transient build difference.

What shipped
  • package.json switched to type: "module" with an exports map exposing ./message and ./constants (plus ./package.json); the dead main: "index.js" and the placeholder npm-init scaffolding are gone.
  • tsconfig.build.json compiles ts/*.ts to dist/*.js and dist/*.d.ts (with declaration maps) under verbatimModuleSyntax.
  • dist/constants.js, dist/message.js, and their declarations are built and committed, so a file: consumer resolves the package without running a build.
  • smoke/runtime-import.mjs proves urd-contract/constants resolves and returns the expected values under plain Node via package self-reference; smoke/typecheck.ts (driven by tsconfig.smoke.json) proves urd-contract/message and urd-contract/constants resolve for a NodeNext TypeScript consumer.
  • make verify now runs build:ts, both smoke checks, and a drift guard that includes dist/. Go build, go vet, and the source typecheck are unchanged.
What it deliberately omits

No CJS output, no npm publish, no change to the Go module or the schema. Go consumers are entirely unaffected: they still import github.com/mariusw/urd-contract. Future TypeScript consumers should import urd-contract/message and urd-contract/constants and never reach into urd-contract/ts/..., which is no longer public API.

v7 - Event envelope for the stack-wide event log (November 2026)

November 2026
in review

A second contract beside Message: the envelope every service uses to publish events into one permanent JetStream stream.

Problem

The plan is to persist metadata from every part of the stack in one replayable log (mariusw/homelab#6), with JetStream as the system of record and any database as a rebuildable projection. That design makes the start date the only irreversible decision: every day without capture is history lost. Capture cannot start without a shared shape, because a log of ad-hoc payloads cannot be queried later, and the contract has to exist before the first producer, not be retrofitted onto several.

Design decisions

The envelope adopts CloudEvents 1.0 in structured JSON mode as prior art rather than inventing field names, with a stricter profile: time, subject and the extension dataversion are required, and source, subject and type are restricted to NATS-safe tokens. Those three form the subject events.<source>.<subject>.<type>. The split between source (who published) and subject (what it is about) is what lets a collector such as Heimdall report on third-party services while each publisher's NATS user is limited to events.<source>.>, so the broker enforces provenance.

It lives in this repository rather than a new one because the schema-to-bindings tooling, the drift guard and CI already exist here, and speed was the priority. The repository name no longer describes everything it holds; renaming it is a separate, later decision. Message is untouched; Event has no versioning field of Message's kind because dataversion versions each payload type independently.

EventSubject is the first hand-written Go function in the repository. It exists because a dot or wildcard in a subject token silently changes NATS routing, so the subject must be built in one checked place. Its patterns duplicate the schema's; the tests and the TypeScript twin keep the three in step.

What shipped
  • event.schema.json, generating event.go and ts/event.ts; make generate and the drift guard cover both contracts.
  • EventsSubjectRoot and EventsStream constants, EventSubject in subject.go, and eventSubject plus the same constants in ts/constants.ts.
  • subject_test.go; make verify now runs go test. The smoke checks cover the new TypeScript surface, exported as urd-contract/event.
  • docs/events.md: the envelope, subject scheme, identity and duplicate handling, payload rules, the recommended EVENTS stream configuration, and an event catalogue with Heimdall's first two types as drafts.
What it deliberately omits

No producer, no stream and no database: those are Heimdall, homelab and later work. The generated Go does not reject unknown top-level attributes, the same as for Message; the schema stays authoritative and the limitation is documented rather than worked around with hand-written decoding.
