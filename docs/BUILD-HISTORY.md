A living document. Add entries chronologically as milestones ship.

## v1 — Contract Repository (June 2026)

**What it was:** The bootstrap of `mariusw/urd-contract` as the single source of truth for the Canonical Message wire format published by every Ratatoskr bridge. Before this repository existed, no shared definition of the Message type existed; the goal of Plan 0 was to make sure ratatoskr, vault, and every other consumer derive the format from one place rather than redefining it locally. This is the foundation every downstream plan depends on.

**Key decisions:** A single JSON Schema (`message.schema.json`) is the authoritative definition; everything else is derived from it. Generated language bindings are checked in (not generated at consume time) so downstream modules can depend on the repo without running codegen, and CI guards that the committed output stays in sync with the schema.

The sharpest decision was how to produce the Go binding. The plan's first choice was `go-jsonschema`, but its output diverged badly from the required wire shape: it named the type `MessageSchemaJson`, used `Id`/`Cwd` casing instead of the idiomatic `ID`/`CWD`, emitted pointer types and custom enum types, attached yaml/mapstructure tags we don't want, and produced an invalid `omitempty,omitzero` tag. Rather than fight the generator with post-processing, the Go struct is hand-authored from the schema and a field-parity test (`generated/go/parity_test.go`) is the correctness mechanism. The test asserts the struct's JSON tags exactly cover the schema's properties and that the required/`omitempty` split matches the wire contract — `git_branch` always present, `parent_session_id` omitted when absent. This keeps "schema is the single source of truth" true for Go without depending on a generator whose output we'd have to override anyway. TypeScript was left on `json-schema-to-typescript`, whose output is clean and deterministic, so it is still genuinely generated by `make generate`.

The stale `go install` path in the plan (`cmd/go-jsonschema`, which no longer exists) became moot once go-jsonschema was dropped from the generate path entirely; CI no longer installs it.

**What shipped:**

- `message.schema.json` — draft-07 JSON Schema defining all eleven Message fields, enums for `harness` and `role`, and `additionalProperties: false`
- `generated/go/message.go` — hand-authored Go struct matching the wire shape, plus `constants.go` (NATS subject, detached-branch sentinel, typed harness/role values)
- `generated/go/parity_test.go` — field-set and required/`omitempty` parity tests against the schema
- `generated/ts/message.ts` (generated) and `generated/ts/constants.ts` (handwritten)
- `Makefile` — `generate` regenerates the TypeScript; `verify` runs the Go tests and fails on any drift between schema and committed generated output
- `.github/workflows/validate.yml` — CI that regenerates and verifies on every push and PR, pinning Go via `go.mod`

**Limitations that drove the next phase:** This repository only defines the contract; it does not yet have a consumer. Plan 1 adds it as a Go dependency to the first bridge. CI has not been exercised against a real remote yet — there is no GitHub remote configured, so the `validate` workflow has only been replicated locally. The parity test covers field names and presence semantics but does not assert type-level correspondence (e.g. that `timestamp` is a `time.Time` mapping to a `date-time` string); that has been acceptable so far because the struct is small and hand-reviewed.

**Gaps identified at review:**

- **No `go vet` or lint step in CI.** For a contract repository that others depend on, a lint pass would be cheap insurance.
- **TypeScript verify doesn't compile-check.** The plan had `npx tsc --noEmit --strict`, but `make verify` only checks git diff. If `json-schema-to-typescript` ever produces invalid TypeScript, it won't be caught until a consumer imports it. Adding a tsc step to verify would close this gap.
- **No versioning strategy.** The contract repo has no semver tags. Once ratatoskr and vault start importing it, there's no way to signal breaking changes. Even `v0.1.0` now would establish the practice.
- **Go module version may cause CI mismatch.** `go.mod` declares `go 1.26.2`, which hasn't been released as stable. The CI uses `go-version-file: go.mod`, so if the runner doesn't have a 1.26 toolchain, the job will fail. Pin to a released Go version.
- **Import path is `generated/go`, not the module root.** Consumers write `contract "github.com/mariusw/urd-contract/generated/go"`. If more Go code is added at the root later, the package structure will need rethinking.

## v2 — Generation Restored (June 2026)

**Problem:** The v1 Go binding was hand-authored, which is the exact opposite of the reason this repository exists. The whole premise is that `message.schema.json` is the single source of truth and every binding falls out of it; a hand-written `message.go` policed by a parity test just recreated the v1/v2 ratatoskr arrangement (a canonical hand-written Go type kept in sync with a second representation) that this repo was built to abolish. The manual-sync debt had changed clothes, not disappeared.

**Root cause, not just the symptom:** The hand-authoring wasn't a tooling failure. The plan specified an exact "required Go struct shape" (idiomatic `ID`/`CWD` casing, plain-string enums, a `Message` type name) lifted almost verbatim from the old ratatoskr hand-written struct. That shape spec was a second source of truth competing with the schema. Once you assert both the schema and the shape of what it must generate, any gap between them forces either generator-fighting or hand-editing. The fix was therefore to delete the requirement, not to satisfy it: stop dictating the Go shape and accept whatever the generator emits as the contract.

The earlier claim that go-jsonschema "couldn't" produce the wanted shape was also just wrong, asserted from memory rather than from `--help`. It has flags for capitalization, tag selection, and root-type naming. But by the root-cause logic above, most of those flags should not be used, because each one imposes a preference the schema does not express. The clean test: configuration that makes the generator honor the schema more faithfully is legitimate; configuration that imposes external taste is a smuggled second authority. Only `-t` survives that test (it tells the generator to take the type name from the schema's own `title`, instead of the file name, which would otherwise yield `MessageSchemaJson`).

**What shipped:**

- `generated/go/message.go` is now genuinely generated by `go-jsonschema -p contract -t`. Accepted as-is: `Id`/`Cwd` casing, pointer optionals, typed `MessageHarness`/`MessageRole` enums with strict unmarshalling, and the default yaml/mapstructure tags. None of these affect the JSON wire format, which is governed solely by the `json` tags.
- `generated/go/parity_test.go` is deleted. It only existed to police a hand-written file; with real generation there is nothing to drift, and CI's regenerate-and-diff is the guard.
- `constants.go` is trimmed to `NATSSubject` and `DetachedBranch`, the only two values the schema cannot express. Harness and role values now come from the generated typed enums.
- `Makefile` `generate` runs both generators; the Go invocation uses `$(shell go env GOPATH)/bin/go-jsonschema` so it works without relying on PATH. CI reinstates `go install github.com/atombender/go-jsonschema@latest` (corrected module path, not the stale `cmd/...` subpath).

**What it deliberately omits:** No attempt to prettify the generated output. `Id`/`Cwd` reads as non-idiomatic Go, but it is lint-exempt generated code with zero wire impact, and matching it to taste is exactly the second-source-of-truth trap that caused this. If a consumer ever needs idiomatic accessors, that belongs in consumer code, not in overriding the generator here.

## v3 — Flattened Layout (June 2026)

**Problem:** Consumers had to import `github.com/mariusw/urd-contract/generated/go`. The word "generated" in a public import path is redundant signaling, the generated-ness is already carried by each file's `Code generated ... DO NOT EDIT` header, and it leaks into the one place it has a cosmetic cost and no functional benefit.

**Design decision:** Drop `generated/` entirely rather than rename it. The Go package moves to the module root, which is Go's own convention for a module's primary package and yields the clean `import "github.com/mariusw/urd-contract"` used as `contract.Message`. TypeScript moves to `ts/`, because TS has no root-package convention and mixing `.ts` beside `.go` at the root just crowds two languages into one directory; TS's path is not a public import identifier, so a subdirectory there costs nothing. The asymmetry (Go at root, TS in `ts/`) reflects each ecosystem's norm rather than being arbitrary.

The rejected alternative was keeping the files under `generated/` and adding a hand-written root package that re-exports them with type aliases. That would reintroduce a hand-maintained surface tracking the schema, the exact second-source-of-truth trap removed in v2. Moving the files has no such cost.

**What shipped:**

- `message.go` and `constants.go` at the module root, package `contract`. Import path is now `github.com/mariusw/urd-contract`.
- `message.ts` and `constants.ts` under `ts/`.
- `generated/` deleted. Makefile `generate` writes to the new paths; `verify` diffs `message.go` and `ts/message.ts`.

This closes the "import path is `generated/go`" gap from the v1 review.
